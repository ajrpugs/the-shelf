# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"The Shelf" is a tiny book-club picker. Signed-in readers (Discord **or Google** OAuth) each set one book; a librarian (a reader holding the librarian role) spins a wheel that randomly picks an eligible reader. Picked readers sit out until the round turns over.

**It is multi-club as of Phase 4** (`docs/multi-tenant-plan.md`): any signed-in reader can create a club at `#/new`, invite people with a code, join at `#/join/<code>`, leave, or delete a club they run. Which club a page is showing comes from the URL (`#/c/<slug>/<tab>`) and which club a *write* touches comes from a `club_id` in the request — never from a constant. `DEFAULT_CLUB_ID` survives only as the fallback for a request that names no club.

There is **no build step and no framework**. The entire frontend is a single `index.html` (~4700 lines) — a vanilla JS ES module that pulls `@supabase/supabase-js` straight from esm.sh and renders everything by hand (including a `<canvas>` spinning wheel). All persistence is Supabase (Postgres + Realtime + Edge Functions).

The club also runs a rubric review system (members score a finished read 1–20 across five categories, averaged into a /100 "Guild score") and per-book comment threads — both layered on top of the same `reads` entries (see below).

## Architecture

**Frontend (`index.html`)** — one file, everything in one `<script type="module">`:
- `SUPABASE_URL` / `SUPABASE_ANON_KEY` are hardcoded constants near the top of the script (anon key is public by design). `CONFIGURED` gates the app when they're placeholders.
- Auth is OAuth via `supabase.auth.signInWithOAuth({ provider })`, where the providers are declared in **`AUTH_PROVIDERS`** — Discord and Google, both live. Adding one is an entry in that array plus dashboard credentials; the gate renders a row per enabled provider. Email accounts are deliberately **deferred**, not pending — see `docs/multi-tenant-plan.md` Phase 5. On sign-in, `ensureUserRow` upserts the reader into `shelf_users` **and `profiles`**.
- `loadAll` fetches this club's `shelf_state` row, `club_members`, `shelf_reviews`, `shelf_comments`, `shelf_comment_reactions`, and `reads` (ordered `ts` desc) in parallel, then does one follow-up `shelf_users` fetch (`.in("id", memberIds)`) for identity and feeds `reads` into `normalizeState` as the history source; `subscribeRealtime` listens to `postgres_changes` on all seven tables and debounces a refresh via `queueRefresh`. Every one of those queries/subscriptions except `shelf_users` is filtered to a hardcoded `DEFAULT_CLUB_ID` constant (see the `clubs` bullet below) — `shelf_users` is global identity with no `club_id` to filter on.
- **The client's `users` array is a join, not a table.** Each entry is a `shelf_users` identity row (`discord_username`, `avatar_url`, `discord_id`) merged with that member's `club_members` row (`book`, `role`) for this club. `render()` consumes the same shape it always did; a `club_members` row whose `shelf_users` identity is missing is skipped. `librarianIds`/`amLibrarian` are derived from the same fetch, so the Admin gate can't drift from the member list being rendered.
- The whole UI is re-rendered by string-building `render()` (with `esc`/`attr` escaping helpers) after every state change.
- The signed-in main view is **tabbed**: `Reading | The Shelf | The Wheel | Leaderboard | Stats | Reviews | Calendar` plus an `Admin` tab that only exists in librarian mode. The active tab is the module-level `currentTab`, kept in sync with the URL: navigating a tab goes through `goToTab(id)`, which sets `location.hash` to `#/c/<slug>/<tab>` (Phase 3 of `docs/multi-tenant-plan.md`, landed 2026-07-27) — `<slug>` is always `DEFAULT_CLUB_SLUG` for now (captured by `parseRoute()` but not yet resolved to a real club; that's Phase 4), so this is a URL-shape change only, not real multi-club routing yet. `parseRoute()` sets `currentTab` from the hash's tab segment on every `render()`, so any programmatic tab switch (the post-draw redirect to Reading, the "jump to a tab" link from a detail page) must also go through `goToTab()` or the next render silently overwrites it back from the URL. Deep-link hash routes (`#book=`, `#shelf=`, `#tag=`, `#reader=`, `#recap`) are a separate, older scheme and still short-circuit `render()` into their own full-page views before the tabs are built.
- `render()` bails early while an `<input>`/`<textarea>` has focus (it defers via `pendingRender`). Any handler that changes state from a button must `document.activeElement?.blur?.()` first — Safari doesn't focus buttons on click, so the re-render would otherwise be silently swallowed.
- Reads go directly to Postgres (RLS allows anon read). **All writes go through Edge Functions** — the client never writes tables directly.
- Book covers are looked up from Open Library (`fetchCoverFromOpenLibrary`) — both client-side for display and server-side for Discord embeds.

**Data model (`supabase/schema.sql`)** — eleven tables:
- `shelf_state` — **one row per club, keyed by `club_id`** (`unique (club_id)`; `id` is still an int PK but auto-assigns from a sequence, so creating a club's state row means naming only its `club_id`). It used to be a hard singleton addressed as `id = 1`; that changed in Phase 3.5, and **nothing should query it by `id` any more**. `data` jsonb holds only `{ eliminated: string[] (user ids), roundNumber: number }` — past reads live in `reads` (below), not here, since the Phase 0 cutover (`docs/multi-tenant-plan.md`). A top-level `version` int column guards against two concurrent admin actions clobbering each other (optimistic locking — see the `admin-update` entry below).
- `reads` — one row per past pick: `round`, `winner_id`, `winner_username`, `book`, `ts`, `rating`, `ratings_open`, `meetings`. This is the source of truth for "past reads" — what used to be `shelf_state.data.history[]`. `ts` is unique per **`(club_id, ts)`**, not globally (Phase 3.5 — a global unique meant one club's draw could hard-fail another's). **`ts` is plain `text`, not `timestamptz`** — it's reused byte-for-byte from the client's `toISOString()` output and is exactly what `shelf_reviews.book_ts` / `shelf_comments.book_ts` join against; casting it to `timestamptz` would make PostgREST re-serialize it differently (`+00:00` vs `Z`) and silently break every review/comment join. Populated by `admin-update`; read directly by the client, `set-review`, `post-comment`, and `calendar-feed`.
- `shelf_users` — one row per Discord-authed reader: `id` (= `auth.users.id`), `discord_username`, `avatar_url`, `book`, `discord_id`. **Identity only** — global, no `club_id`, one row per human across all their clubs. `discord_id` links a web account to a Discord user for the slash command. **The `book` column is a legacy mirror as of Phase 3.5 and nothing reads it** — the reader's current book lives on `club_members.book` (a person in two clubs has two books). Writers keep it in step only so the cutover stays reversible; it goes away in Phase 6. Deleting a row here removes the person from *every* club, which is why `admin_remove_user` no longer does that.
- `shelf_reviews` — one rubric review per (club, read, reader), primary-keyed `(club_id, book_ts, user_id)` — so upserts must pass `onConflict: "club_id,book_ts,user_id"`. Five category scores (`plot`, `characters`, `pacing`, `language`, `themes`), each 1..20, plus an optional `note`. `book_ts` keys to `reads.ts` by exact string match (not a real foreign key — see the state-shape gotchas below). Written via the `set-review` edge function (or bulk-imported by a librarian via `admin_import_reviews`); readers may also insert/update/delete their own row directly under RLS. A row is either scored (all five categories non-null) or a `dnf` (didn't-finish) row, which carries `dnf = true` and all five categories null — a check constraint (`shelf_reviews_dnf_scores_chk`) keeps the two shapes mutually exclusive. DNF rows are excluded from every score aggregate (`aggregateRubric`, `reviewSuperlatives`, `bookBadges`, a reader's own average score given) but still count toward review/participation counts.
- `shelf_comments` — per-book discussion thread, keyed to a read by `book_ts` (same exact-string-match scheme as `shelf_reviews`, against `reads.ts`). Written via the `post-comment` edge function; readers may insert their own and delete their own under RLS. `parent_id` (nullable, `on delete cascade`) makes a comment a reply to another comment — threading is **single-level**: a reply's own `parent_id` must be null, enforced by `post-comment` (not the DB, since a check constraint can't look at other rows). Deleting a top-level comment cascades to its replies.
- `shelf_comment_reactions` — emoji reactions on comments, primary-keyed `(comment_id, user_id, emoji)`. No service-role logic or Discord side effects, so signed-in readers write these straight to the table under RLS (insert/delete their own row). Applies equally to top-level comments and replies (keyed by `comment_id` alone, agnostic of `parent_id`).
- `shelf_librarians` — presence of a `user_id` row = librarian (see "Librarian is a role, not a password" below). No write policy at all — reads for authenticated users, writes only through `admin_grant_librarian` / `admin_revoke_librarian`.
- RLS: anyone (anon) can **read** `shelf_state`/`shelf_users`/`shelf_reviews`/`shelf_comments`/`reads`/`clubs`; signed-in users can read `shelf_librarians`. A reader may insert/update only their own `shelf_users`/`shelf_reviews` row, or insert/delete only their own `shelf_comments` row. `shelf_state`/`reads` mutations happen only via service-role Edge Functions. As of Phase 1 slice 3, the select policy on `shelf_state`/`shelf_reviews`/`shelf_comments`/`shelf_comment_reactions`/`reads`/`club_members` is no longer a blanket `using (true)` — it's `is_member(club_id) or clubs.visibility = 'public'`. The existing club stays anon-readable only because its seeded `clubs` row defaults to `visibility = 'public'`; `clubs` itself and `shelf_users`/`shelf_librarians` keep their original unscoped policies.
- `clubs` — one seeded row (fixed id `8fdb4e0f-ea2f-4a45-9d9a-059a3292b3f8`, slug `the-guild`, name "The Guild", `visibility = 'public'`) plus a `club_id` column on `reads`/`shelf_state`/`shelf_reviews`/`shelf_comments`/`shelf_comment_reactions`, constant-defaulted to that same id. `shelf_users` stays deliberately unscoped — it's identity, one row per human regardless of how many clubs they're in. **Which club a request acts on is now data, not a constant** (Phase 4 slice 4b): the client resolves the slug in `#/c/<slug>/…` against this table and sends the resulting id as `club_id` on every edge-function call. `DEFAULT_CLUB_ID` survives in both halves only as the fallback for a request that names no club, which is what lets the frontend and the functions be deployed in either order. `clubs` itself keeps an unscoped `using (true)` select policy on purpose, so a reader can resolve a club they were linked to before anyone knows whether they belong to it.
  - **A caller naming its own club is only safe because every function re-authorizes against it.** `admin-update` requires `club_members.role = 'librarian'` for the club in the body; `set-book`, `set-review` and `post-comment` require membership of it. Never add a club-scoped action without that check — and note `set-book` deliberately *updates* rather than upserts the membership row, because an upsert would let any caller insert themselves into any club and appear on its shelf. Joining is Phase 4d's job.
  - `discord-interactions` is the one exception: a slash command carries a guild and a Discord user, never a club, so it stays pinned to the seeded club until Phase 6 teaches `clubs` its Discord guild id.
- `club_members` — **the source of truth for who is in a club, their `role`, and their current `book`** (as of Phase 3.5; it was a best-effort mirror before). Backing table for the `is_member()` RLS policy function, for `admin-update`'s own librarian check (a plain `.eq("club_id", ...).eq("user_id", ...)` query against `role`, run with the service-role client — not the `is_librarian()` SQL function, which exists but is used by `club_invites`' select policy rather than by this check), for the client's Admin-tab gate, and for `draw`'s eligible-reader pool. **The write direction is now the reverse of what it was**: the `club_members` write is the one that must succeed, and `shelf_users.book` / `shelf_librarians` are best-effort mirrors that nothing reads. A member's presence in this table (not their `role`/`book` values) is what `is_member()` checks.
  - The table has **no insert policy** (same reasoning as `shelf_librarians`' write side), so the only ways in are `club-admin`'s `join_with_invite` (Phase 4d) and `create_club` (4c, which makes you its librarian). **Signing in joins you to nothing.** It used to: `join_default_club()` added every new account to the seeded club, which was right with one club and wrong the moment anyone could create their own — it made strangers members of somebody else's club, on its shelf and in its wheel. The RPC was dropped, not merely unused, since `security definer` + execute-to-`authenticated` meant any caller could invoke it directly (`20260809170000`). **A reader with no row here is invisible to the app entirely** — not on the shelf, not on the wheel — and now lands on the "you're not in a book club yet" screen instead.
- `profiles` — identity separate from any one club (`id`, `display_name`, `avatar_url`, `discord_id`). Closes one of the two schema gaps `docs/multi-tenant-plan.md` Phase 1 was left owing. **Written live** as of the Phase 5 prep: `ensureUserRow` upserts it on every sign-in alongside `shelf_users` (best-effort — nothing reads it yet, so a failure there isn't worth interrupting sign-in over). It stopped being the one-time backfill snapshot it was, but `shelf_users` is still the table everything actually *reads*; the flip is slice 5b, where an email signup with no provider metadata gets asked for a display name and needs somewhere provider-agnostic to put it. RLS mirrors `shelf_users`: read for all, insert/update only your own row (verified — writing someone else's row is a 42501).
- `club_invites` — invite codes (Phase 4 slice 4d). `code` is the primary key **and the credential**: 12-char Crockford-ish base32 minted by `club-admin`. Optional `expires_at`/`max_uses`, plus `uses` and `revoked`; an invite is unusable when revoked, expired, or out of uses — all three checked at join time rather than by a constraint, so a spent invite stays visible in the Admin tab as history. Its select policy is **`is_librarian(club_id)`, not `is_member`** — any member being able to list codes would defeat invite-only. That policy is the first (and only) RLS policy in the app that asks about a role, which is why `is_librarian()` finally exists after being deferred since Phase 2.
- `club_secrets` — per-club secrets (`discord_webhook_url`, `calendar_token`), primary-keyed on `club_id`. The other schema gap Phase 1 owed. **No RLS policies at all** — unreachable from anon/authenticated, service-role only, same reasoning as `shelf_librarians`' write side. Additive only: nothing reads `discord_webhook_url` yet (the real webhook is still the `DISCORD_WEBHOOK_URL` env secret until Phase 6 wires per-club webhooks into `admin-update`/`set-book`/`discord-interactions`) and `calendar-feed` doesn't consume `calendar_token` yet either — the seeded club already has a row so nothing has to remember to backfill it later.

`supabase/functions/_shared/shelf-logic.mjs` holds the pure draw/undo/rating/meeting decision logic (eligibility picking, round-advance/rollback math, rating/meeting validation), extracted out of `admin-update` and covered by `node --test supabase/functions/_shared/*.test.mjs` (**glob the files, not the bare directory** — Node ≥23 treats a bare directory path as a module to load and fails with `MODULE_NOT_FOUND`). Written in plain `.mjs` (not `.ts`) so it's both a valid Deno import at deploy time and directly runnable under local Node with zero tooling.

**Edge Functions (`supabase/functions/`)** — Deno, deployed individually:
- `admin-update` — librarian-gated writes to `shelf_state`/`reads`. Verifies the caller's JWT itself (that's why it deploys `--no-verify-jwt`, same as `set-book`), requires `club_members.role = 'librarian'` for the caller at `DEFAULT_CLUB_ID` (else 401 no token / 403 not a librarian) — club-scoped, not the global `shelf_librarians` table (see the `club_members` bullet above) — then uses the **service role key**. Actions: `draw`, `new_round`, `reset`, `undo_last_spin`, `admin_clear_book`, `admin_set_book`, `admin_set_rating`, `admin_set_ratings_open`, `admin_set_meeting`, `admin_announce_meeting` (re-posts a read's existing dates to Discord without changing them — the no-op guard on `admin_set_meeting` means an identical re-save stays silent, so this is the way to (re)announce), `admin_import_reviews` (bulk-upsert member rubric reviews into `shelf_reviews`, keyed by `book_ts` + `user_id`), `admin_grant_librarian` / `admin_revoke_librarian` (set `club_members.role` for this club, mirroring into `shelf_librarians`; a librarian can't revoke themselves), `admin_remove_user` (deletes the **membership**, not the global `shelf_users` identity row — doing the latter would remove the person from every club they belong to; they rejoin by signing in again, same as before). `draw` picks a random reader with a book set who isn't in `eliminated` — the pool is **this club's `club_members` rows**, joined to `shelf_users` only for the winner's display name/avatar/`discord_id`, never a sweep of `shelf_users` — and **auto-advances the round** when that pick empties the eligible pool. Fires a Discord webhook after a durable `draw`, again after `admin_set_meeting` when the schedule actually changed, and again after `admin_set_rating` when the committed score actually changed (each of these three no-op guards means an identical re-save stays silent). Meeting times are posted as Discord `<t:unix:F>` markup so each member sees them in their own timezone; the rating post includes the /100 total, its band, and the per-category breakdown when present. All three posts happen **after** the state write and swallow their own errors — a dead webhook must never fail the librarian's action.
  - **Only `draw`, `new_round`, `reset`, `undo_last_spin`, and `admin_remove_user` touch `shelf_state`** (they're the ones that change `eliminated`/`roundNumber`), and each does so through a `writeGameState()` helper that conditions the write on `shelf_state.version` (`.eq("version", currentVersion)`, bumping it by one) — a 409 means another admin action landed first; the client shows "try again." **The versioned write always happens before any corresponding `reads` mutation** (insert for `draw`, delete for `undo_last_spin`/`reset`) — if the version check fails, nothing in `reads` is touched, so there's no window where a pick is recorded without `eliminated` reflecting it. The other actions (`admin_set_rating`, `admin_set_ratings_open`, `admin_set_meeting`, `admin_announce_meeting`, `admin_clear_book`, `admin_set_book`) only ever touch `reads`/`shelf_users` directly and skip the `shelf_state` write entirely — guarding it uniformly would risk a false 409 on an action whose real (already-committed) mutation had nothing to do with `eliminated`/`roundNumber`.
  - Every action's response reconstructs `history` fresh from `reads` (`order by ts desc`, aliasing `ratingsOpen:ratings_open`) before returning — this keeps `{ state: { eliminated, roundNumber, history }, winner, roundAdvanced }` byte-for-byte the same response shape the client has always consumed, so `normalizeState(body.state)` on the client needed no changes for the cutover.
- `set-book` — a signed-in reader sets/clears their own book. Verifies the JWT itself (pulls the user id out), then writes with the service role and posts to Discord. Deployed `--no-verify-jwt` for its own error handling.
- `discord-interactions` — receives Discord slash-command webhooks (`/mybook`). **Must** verify Discord's Ed25519 signature (`DISCORD_PUBLIC_KEY`) or Discord rejects the endpoint. Looks the reader up by `discord_id`, sets their book, and posts the same Discord embed `set-book` would.
- `set-review` — a signed-in reader submits (or clears) their own rubric review for the *current* read. Verifies the JWT itself. Only accepted while the read is the oldest unrated history entry **and** the librarian has `ratingsOpen` on it (`admin_set_ratings_open`); clearing (`clear: true`) is allowed anytime and just deletes the caller's own `shelf_reviews` row. Deployed `--no-verify-jwt`, same pattern as `set-book`.
- `post-comment` — a signed-in reader posts (or deletes their own) comment on a book's discussion thread, keyed by history `ts`. Verifies the JWT itself. Deployed `--no-verify-jwt`.
- `club-admin` — the club lifecycle (Phase 4 slices 4c–4e) plus account deletion (6b): `create_club`, `create_invite`, `revoke_invite`, `join_with_invite`, `leave_club`, `delete_club`, `delete_account`. **`delete_account` is the only action that takes no `club_id`** — it spans every club the caller is in, requires the phrase "DELETE MY ACCOUNT", and refuses anyone who is the sole librarian of *any* club (the `leave_club` guard, applied across all of them; without it an account deletion orphans clubs with no UI to appoint a replacement). It deletes the `auth.users` row and lets the cascades do the rest — `reads` deliberately survives with `winner_id` nulled and `winner_username` as text, so a club's ledger doesn't grow holes when someone leaves the product. **Separate from `admin-update` on purpose** — that function is gated on "librarian of this club", which is the wrong question for `create_club` (no club yet) and `join_with_invite` (performed by a non-member by definition). Each action states its own gate. Holds the rules the client must not be trusted with: slug shape + the reserved-word list, 3 clubs per user per rolling day, invite validity, and "the last librarian may not leave". `create_club` builds `clubs` + `shelf_state` + founding `club_members` + `club_secrets` together and **deletes the club it just made if any later step fails** — PostgREST has no cross-statement transaction, and a half-built club would squat its slug forever. `delete_club` needs the club's name typed back and relies on the `on delete cascade` FKs added by `20260809160000`. Deployed `--no-verify-jwt`.
- `calendar-feed` — public, read-only **iCalendar (`.ics`) feed** of one club's meetings, built from `reads`. Emits one `VEVENT` per scheduled 50%/100% meeting. Deployed `--no-verify-jwt` because calendar clients (Google/Apple/Outlook) can't send a Supabase apikey — which is also why the club is selected by an unguessable **`?token=<club_secrets.calendar_token>`** rather than by auth. An unknown token is a 404; a *missing* token falls back to `DEFAULT_CLUB_ID` (never to "all clubs") so the URLs members already have in their calendar apps keep working. The client still emits the token-less URL, because `club_secrets` has no RLS policies and is genuinely unreadable from the browser — surfacing a real per-club token needs a librarian-only endpoint (Phase 6), which is also when the fallback goes away. Event `UID`s are deliberately *not* club-scoped: changing a UID makes every calendar client duplicate the event for existing subscribers. `GET` only.

`admin-update`, `set-book`, and `discord-interactions` each carry their own copy of the Open Library cover lookup + Discord embed helpers (`normalizeForMatch`, `parseTitleAuthor`, `fetchCover`, `postBookSet`) — those three (and only those three) post to Discord. If you change cover-matching or embed formatting, **change it in all three copies**. `set-review` and `post-comment` don't touch Discord at all.

### State-shape gotchas
- `shelf_state.data` holds only `{ eliminated, roundNumber }` and is edited as a whole object, not per-field — read it, mutate the object, write it back (guarded by `version`, see below). Past reads (`history`) live in the `reads` table instead — a client-side `state.history` array is still assembled at read time (in `loadAll` and in every `admin-update` response), it's just sourced from `reads` rows rather than a jsonb blob.
- `eliminated` and `reads.winner_id` hold **user ids** (uuid), not names. Older name-based entries (from before the Discord OAuth migration) are tolerated by the `reads` backfill migration and by the client's `normalizeState`, which also maps legacy `cycle`/`cycleNumber` → `round`/`roundNumber`.
- **Never change `reads.ts` to `timestamptz`.** It's `text` on purpose — it's reused byte-for-byte from the client's `toISOString()` output and is exactly what `shelf_reviews.book_ts` / `shelf_comments.book_ts` compare against with `===`/`eq()`. A timestamptz column gets re-serialized by PostgREST (`2026-07-24T20:00:00+00:00`, not `...000Z`) on every read, which would silently break every review/comment join.
- **`normalizeState`'s per-history-item field mapping now only exists client-side** (`index.html`). The server-side copy in `admin-update` shrank to `normalizeGameState`, which only touches `eliminated`/`roundNumber` — it no longer models individual reads at all, since those come straight from typed `reads` columns. Any new per-read field still only needs to be added in one place (the client's `normalizeState` and the `admin-update` response's `.select(...)` alias list), not two.
- Meetings live on the read: `reads.meetings = { half: { at, upTo }, full: { at } }` (jsonb column). `at` is an **ISO instant**. `upTo` (the "read up to Chapter 12" checkpoint) exists only on `half`.
- **Meeting times are pinned to `America/Toronto` (`CLUB_TZ`), not the browser's zone** — the club meets Wednesdays 8pm ET, and that must read the same for a librarian or member in any timezone. `clubWallToInstant` / `toClubInputValue` convert between Toronto wall-clock and UTC instants via `Intl.DateTimeFormat`, so DST (EST↔EDT) is handled; never use bare `new Date("...T20:00")` on a `datetime-local` value, and never let the edge function parse one (its local time is UTC, so it would read `T20:00` as 8pm UTC).
- `undo_last_spin` has to detect whether the undone pick had auto-advanced the round and roll `roundNumber` back accordingly (`rollbackUndo` in `_shared/shelf-logic.mjs`).
- The **"current read"** for reviewing purposes is the oldest `reads` row without a committed `rating` — i.e. rows are fetched newest-first (`order by ts desc`), so it's the *last* unrated item, not the first. Both `set-review` and the client compute it the same way; a member can only submit a review against that entry, and only once the librarian has flipped `ratings_open` on it via `admin_set_ratings_open`.
- `shelf_state.version` is an optimistic-locking token, not app data — it only matters inside `admin-update`'s `writeGameState()` helper. Don't expose it to the client or try to reason about its value outside that one function.
- **There is no `.btn` class, and `--card`/`--ink` are both cream.** Two traps that cost a round of visibly broken UI. The house button styles are `.btn-primary`, `.btn-ghost`, `.btn-danger`, `.btn-mini`, `.btn-provider` — `class="btn"` silently renders a default browser button on dark felt. And this is a **single dark theme**: `--card` (#f6ecd0) is a cream *foreground/button* colour for use on the dark felt, `--ink` (#ece3cf) is cream *text for dark panels*. Pairing them as background/colour produces cream on cream. For a light button use `--felt-dark` text on `--card`; for a highlighted pill use `--ink` on `--panel-2`. **Check a new `var(--x)` is actually defined** — an invalid `var()` invalidates the whole declaration, so a mistyped token means the rule silently does nothing (`--rule` didn't exist and killed two borders).
- **Look at the page.** The three UI defects above all shipped because CSS was written against tokens and classes that were never verified and screens that were never opened. `python3 -m http.server` plus the Chrome tools renders the signed-out gate without any credentials, which is enough to catch this class of thing.
- **Discord's OAuth `prompt` defaults to `consent`**, so its authorise screen reappears on *every* sign-in unless `prompt=none` is sent — but `prompt=none` errors instead of prompting when the account hasn't authorised the app yet, so it can't be sent unconditionally. `signIn()` sends it only when `localStorage` records a completed sign-in with that provider in this browser (`shelf:oauth-seen:<provider>`), set on the `SIGNED_IN` event. If the flag goes stale (access revoked in Discord), the attempt returns an OAuth error, which `initAuth` reads out of the URL — **before `createClient` runs, since `detectSessionInUrl` consumes the fragment** — then clears the flags so the next click is an ordinary consent flow. Covered by `tests/client-oauth-consent.test.mjs`.
- **`user_metadata` describes the most recent provider, not the account.** It is overwritten on each sign-in, so a reader who links a second provider has metadata describing *that* one. Never derive a provider-specific id from it: `discord_id` comes from `discordIdFromUser()`, which reads the authoritative per-provider `identities` array and only falls back to metadata when `app_metadata.provider === "discord"`. The old code read `user_metadata.provider_id || .sub`, which would have written a **Google** subject id into `shelf_users.discord_id` — the column `/mybook` looks readers up by, and unique on `profiles` — so a Google sign-in could overwrite a real Discord id or fail on the unique constraint. Covered by `tests/client-identity.test.mjs`.
- **A reader's book is on `club_members.book`, not `shelf_users.book`.** Anything that sets or clears a book writes the membership row (fatal on error) and mirrors `shelf_users.book` best-effort. Anything that *reads* a book must use `club_members`, or it will silently read a stale mirror. This is why `set-book` upserts rather than updates — a reader who signed in but never joined has no membership row.
- **Before any `supabase db push`**: run `scripts/backup.sh` (the project has no automatic backups at all — see Backups) and `scripts/rehearse-migrations.sh <new migration>` (applies it to production inside `BEGIN … ROLLBACK`, so a migration that would fail, or would change rows you didn't expect, is caught with nothing committed).
- **Deployment order matters when changing anything touching `reads`/`shelf_state`**: DB migrations (`supabase db push`) must land before either the edge-function deploys or the frontend push. Within Phase 3.5 specifically, the `shelf_reviews` primary-key swap means the currently-deployed `set-review`/`admin-update` (passing `onConflict: "book_ts,user_id"`) start erroring the moment the migration lands, so **deploy those two immediately after `db push`** — review submission and review import are broken in between. Everything else in that batch is filter-only; `post-comment`/`calendar-feed` and the frontend can land in any order relative to each other, since their response/payload contracts are unchanged.

## Common commands

No build step and no dependencies to install for the app itself. The toolchain is only for verification and backups — none of it is needed to run or deploy:

```bash
brew install node deno          # tests + typechecking the edge functions
brew install colima docker      # only for pg_dump-based backups; see "Backups"
colima start                    # headless Docker VM (colima stop when done)
```

Colima rather than Docker Desktop deliberately: CLI-only, no GUI launch, no licensing step. `supabase db dump` and `supabase start` are the only things that need it.

```bash
# Typecheck the edge functions (the Supabase deploy pipeline only transpiles, so
# this is the only thing that catches type errors in them)
deno check --no-lock supabase/functions/*/index.ts

# Offline unit tests: shared draw/undo/rating/meeting logic, plus the client's
# post-auth redirect (sliced out of index.html at run time, so it tests what ships)
node --test supabase/functions/_shared/*.test.mjs tests/*.test.mjs

# Run the frontend locally (nothing to build — Supabase is the backend)
python3 -m http.server        # then open http://localhost:8000/index.html

# Deploy an edge function (each is deployed by name; --no-verify-jwt is required).
# TMPDIR MATTERS: the bundler writes its eszip under $TMPDIR from inside a
# container, and Colima does not mount /var/folders (macOS's default TMPDIR), so
# the deploy dies with "failed to open eszip: ENOENT". Point TMPDIR at something
# under $HOME, which Colima does mount:
#   export TMPDIR=$HOME/tmp && mkdir -p "$TMPDIR"
supabase functions deploy admin-update --no-verify-jwt
supabase functions deploy set-book --no-verify-jwt
supabase functions deploy discord-interactions --no-verify-jwt
supabase functions deploy set-review --no-verify-jwt
supabase functions deploy post-comment --no-verify-jwt
supabase functions deploy calendar-feed --no-verify-jwt
supabase functions deploy club-admin --no-verify-jwt

# Manage server-side secrets (never in the HTML)
supabase secrets set DISCORD_WEBHOOK_URL='...'
supabase secrets set DISCORD_PUBLIC_KEY='...'      # from the Discord app portal

# Back up production BEFORE any db push (see "Backups" below -- this is the only
# restore point the club has). Verifies row counts and exits non-zero on drift.
scripts/backup.sh

# Dry-run migrations against real production schema + data, then roll back.
# Nothing is committed. Do this before every db push.
scripts/rehearse-migrations.sh supabase/migrations/<new>.sql

# Apply schema / migrations

# Local database (needs Colima; -x vector is required -- see "Local database")

supabase db reset          # replays every migration from scratch

# Run the RLS cross-tenant isolation check. Hits the LINKED live project (it

node --test supabase/tests/rls-isolation.test.mjs
```

## Backups

**The project has no automatic backups.** `supabase backups list` reports `pitr_enabled: false` and an empty backup list — that's the plan tier, and it means a bad `reset` or a bad migration is unrecoverable by default. Upgrading to Pro (for PITR/daily backups) is the real fix and is still open in `docs/multi-tenant-plan.md` §6.

Until then, `scripts/backup.sh` is the restore point:

- Goes through `supabase db query`, **not** `supabase db dump` — the latter runs `pg_dump` inside Docker, and there's no Docker on this machine.
- The whole snapshot is one query, so it's a single consistent transaction. Emits one INSERT per table into `~/the-shelf-backups/<timestamp>/restore.sql`, rebuilding rows via `jsonb_populate_recordset` so a later column reorder can't corrupt a restore.
- **Verifies row counts against live and exits non-zero on any mismatch.** The SQL lives in `supabase/backup-sql/`; if you add a table, add it to both files there or it silently won't be backed up (the count check only compares tables it's told about).
- Written outside the repo deliberately: it contains `club_secrets` (Discord webhook URL, calendar token) plus every member's name, book, reviews and comments. Keep it out of git and off shared drives.
- **`auth.users` is not included** — Supabase manages it. Restoring into a fresh project means members sign in again, which mints new ids and orphans every `winner_id`/`user_id` in the file. A restore is only turnkey back into the *same* project.

**Scheduled backups** run daily at 13:00 via a user LaunchAgent, `net.sh3lf.backup`. Install/refresh with `scripts/install-backup-agent.sh`, remove with `--remove`. Log: `~/the-shelf-backups/backup.log`.

- It runs a **staged copy** under `~/Library/Application Support/the-shelf-backup/`, not the repo. This isn't tidiness: the repo lives in `~/Documents`, which macOS TCC protects, and a LaunchAgent cannot read it at all — the job dies with exit 126 / `Operation not permitted` before the first line runs. Granting Full Disk Access would also work but is a manual System Settings step.
- **The staged copy is a snapshot — re-run the installer after editing `scripts/backup.sh` or `supabase/backup-sql/`**, or the scheduled job keeps using the old versions.
- It sets `SUPABASE_PROJECT_ID` rather than relying on `--linked` (there's no `supabase/.temp/` outside the repo), and `TMPDIR=$HOME/tmp` for the same Colima reason as function deploys.
- It starts Colima if Docker is down so the pg_dump half still happens, then stops it again — verified end to end from cold (~67s).
- Retention keeps the newest 14 runs, pruning only after a run has verified, so a failed run can never evict a good backup.
- **`supabase db query --output-format json` returns a bare array** (`[{...}]`), not `{rows: [...]}`. Some wrappers re-wrap it; the parsing in `backup.sh` accepts both on purpose. Don't "simplify" it — coding against only the wrapped shape breaks the script everywhere except inside that wrapper.
- Honest limits: it only fires while this Mac is awake and logged in, and depends on the CLI's stored credentials staying valid. Not a substitute for Pro's PITR.

Reversing a schema change is separate from restoring data: hand-run rollback scripts live in `supabase/rollback/` (deliberately outside `supabase/migrations/` so `db push` can't apply them).

Note `schema.sql` is maintained by hand alongside each migration — it is the bootstrap document, not generated output, so a new migration must be mirrored into it as a new numbered section.

## Local database

`supabase start -x vector` then `supabase db reset` gives a local Postgres with the full schema (verified: 11 tables, 21 policies, `is_member`/`join_default_club`, the Phase 3.5 constraints, seeded club). Use it for anything that would otherwise mean creating throwaway rows in the live club. Needs Colima running.

- **`-x vector` is required with Colima.** The `supabase_vector` container bind-mounts the Docker socket, and Colima's socket is a forwarded file it can't mount: `operation not supported`. Without the flag, `supabase start` fails after applying every migration.
- This only works because of `00000000000000_bootstrap_base_tables.sql`. `supabase/migrations/` was never a complete history — the first real migration does `alter table public.shelf_users`, but nothing created it (the base schema came from pasting `schema.sql` into the SQL editor), so a from-scratch apply died on migration 1. The bootstrap migration supplies `shelf_state`/`shelf_users` as they were *before* that migration, and is recorded on production as already-applied via `supabase migration repair --status applied 00000000000000` rather than run.
- `20260724120000_add_shelf_librarians.sql` seeds a hardcoded **production** user id as the first librarian. It's now guarded by an `auth.users` lookup, because on any other database that FK aborted the whole chain with a 23503. On a fresh local DB you get no librarian — create one by hand (see "Librarian is a role" above).

Pre-deploy validation still uses `scripts/rehearse-migrations.sh` (BEGIN … ROLLBACK against production) as well as the local DB: the local one proves a migration *applies*, the rehearsal proves it applies **to the real data** without changing row counts.

## Secrets & config

- **Public / in the HTML:** `SUPABASE_URL`, `SUPABASE_ANON_KEY` — safe to commit.
- **Server-side only (Supabase secrets):** `DISCORD_WEBHOOK_URL`, `DISCORD_PUBLIC_KEY`. `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` are injected into functions automatically.
- **Sign-in providers live in `AUTH_PROVIDERS`** (`index.html`): Discord and Google, both `enabled: true`. Adding one is an array entry plus credentials in the Supabase dashboard — the gate renders a row per enabled provider and drops its Discord-specific copy once there's more than one. `enabled` is a deploy-time switch, not feature detection: there's no way to ask Supabase whether a provider is configured, and a live-looking button that errors is worse than an absent one. **Email/password accounts are deliberately deferred** (`docs/multi-tenant-plan.md` §4) — they'd need a transactional-email provider, which password reset makes non-optional, and Google already covers the audience email was for.
- **Supabase links a second provider onto an existing account** when the email matches and is verified — measured on production, not assumed: adding Google to a Discord reader left `auth.users` unchanged, produced one user with two identities, and preserved every `discord_id`. That last part only held because `discordIdFromUser()` reads the `identities` array; the older metadata-based code would have overwritten a real Discord id with a Google one.
- **Librarian is a per-club role, not a password.** A librarian is a reader whose `club_members` row for that club has `role = 'librarian'`. **Both sides now read the same table**: `admin-update` checks `club_members.role` for `DEFAULT_CLUB_ID`, and so does the client's `amLibrarian` gate (as of Phase 3.5 — it used to read the global `shelf_librarians` table, so the UI would have offered the Admin tab to a librarian of some *other* club even though the server correctly 403'd them). `shelf_librarians` still exists and is still mirrored by grant/revoke, but **nothing reads it any more**. Signed-in users can read the role list (the Admin tab shows each reader's status and offers grant/revoke); `club_members` has no write policy, so grants/revokes only happen through the two edge-function actions. Roles deliberately do **not** live on `shelf_users` (its "update self" policy would let a member self-promote). **Bootstrapping the very first librarian on a fresh deployment is one insert:**
  ```sql
  insert into club_members (club_id, user_id, role) values ('8fdb4e0f-ea2f-4a45-9d9a-059a3292b3f8', '<auth user id>', 'librarian')
    on conflict (club_id, user_id) do update set role = 'librarian';
  ```
  After that, grants/revokes should go through the Admin tab, which keeps the `shelf_librarians` mirror in sync too.
